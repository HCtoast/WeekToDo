# 개발 계획

기획서: [../weekly-timeblock-widget-spec.md](../weekly-timeblock-widget-spec.md)
프로젝트 규약: [../CLAUDE.md](../CLAUDE.md)

## 전략

이 앱의 난이도는 UI가 아니라 **"앵커 + 상대 큐 + 고정 장애물"이라는 시각 계산 모델**에 있다.
그래서 순서를 이렇게 잡는다.

1. 계산 엔진을 순수 함수로 먼저 만들고 테스트로 고정한다.
2. 그 위에 읽기 전용 UI를 얹는다.
3. 그 다음 인터랙션(드래그·홀드)을 붙인다.
4. 구글 연동은 **가장 마지막**에 붙인다.

구글 연동을 뒤로 미루는 이유: OAuth 설정·네트워크·레이트리밋 때문에 개발 루프가 느려지는데, 밀림 로직 입장에서 구글 이벤트는 그냥 "시각이 고정된 블록 배열"일 뿐이다. Phase 2에서 목 데이터로 동일한 인터페이스를 쓰면 나중에 실제 API로 갈아끼우는 것만 남는다.

각 Phase는 그 시점에 **실행해서 눈으로 확인 가능한 상태**로 끝난다.

## Phase 1 — 데이터 계층 ✅ 완료

스키마를 코드로 확정한다.

- [x] 마이그레이션 러너 (`user_version` PRAGMA, 마이그레이션당 트랜잭션 1개)
- [x] `001_init.sql`: 7개 테이블 + 인덱스
- [x] 기본 카테고리 6종 시드 (과제·일상·개발·여가·쇼핑·기타)
- [x] `settings` — **기본값을 시드하지 않는 override 방식** (아래 참고)
- [x] `shared/types.ts` 행 타입, `shared/settings-schema.ts`, `shared/color.ts`
- [x] repository: `settings`, `categories`
- [x] `PRAGMA foreign_keys = ON`, `journal_mode = WAL`

**settings를 시드하지 않는 이유**: 기본값의 출처를 `shared/settings-schema.ts` 하나로 두기 위함. DB에도 기본값을 넣으면 출처가 둘이 되어, 나중에 기본값을 바꿔도 기존 사용자에게 반영되지 않는다. 그래서 `settings` 테이블은 **기본값에서 벗어난 값만** 담고(= anchors와 같은 override 방식), 값이 기본값으로 되돌아가면 행을 지운다. 새 설정 키를 추가할 때 마이그레이션이 필요 없다는 이점도 따라온다.

**repository 범위**: `local_events` / `todos` / `todo_time_slots` / `google_event_cache`의 repository는 그것을 실제로 쓰는 Phase(3·4·7)에서 함께 만든다. 소비자 없이 미리 CRUD를 다 짜두면 실제 쿼리 패턴과 어긋난 채로 방치되기 쉽다. 스키마는 이미 확정됐으므로 나중에 붙여도 스키마가 흔들리지 않는다.

기획서 스키마 대비 확정된 변경 (근거는 [../CLAUDE.md](../CLAUDE.md#기획서-대비-확정-변경점)):

```sql
-- anchors: 요일 기본값에 대한 override 기록. 날짜당 최대 1행.
ALTER ... anchors.date  → UNIQUE
         anchors.source → 'manual' | 'autostart'   -- 'fixed'는 행 없이 파생되므로 저장 안 함

-- local_events: 앵커가 아니라 날짜에 매단다
- anchor_id TEXT NOT NULL REFERENCES anchors(id)
+ date      TEXT NOT NULL                      -- 'YYYY-MM-DD', 논리적 날짜
+ completed    INTEGER NOT NULL DEFAULT 0
+ completed_at TEXT NULL

-- categories: 완료 체크박스 노출 여부
+ completable INTEGER NOT NULL DEFAULT 0        -- 시드: 과제만 1
```

`settings` 신규 키:

| key | 설명 | 기본값 |
|---|---|---|
| `weekdayAnchorTimes` | 요일별 기본 앵커 시각 (자동 설정이 없을 때의 fallback) | `{"mon":"19:00","tue":"19:00",…,"sun":"19:00"}` |
| `autoAnchorOnLaunch` | 시작앱 자동 실행 시각으로 앵커를 자동 설정할지 | `true` |

기존 `fixedAnchorTime` 단일 키는 폐기한다. 올림 단위(30분)는 `shared/constants.ts`의 `ANCHOR_SNAP_MINUTES`로 둔다.

**완료 기준**: 앱을 켜면 DB가 마이그레이션되고 시드 카테고리가 조회된다. → **확인됨** (`user_version 1/1`, 테이블 7개, 시드 6종, 재기동 시 마이그레이션 건너뜀)

**테스트 범위 주의**: `better-sqlite3`는 **Electron ABI**로 빌드되므로 일반 Node에서 도는 vitest가 `require`할 수 없다. 따라서 repository는 vitest로 덮지 않는다. 대신 로직을 순수 함수로 뽑아 `shared`에서 테스트하고(설정 파싱·검증, 색상 파생), repository에는 SQL만 남긴다. DB 경유 동작은 앱 확인 화면으로 검증한다.

## Phase 2 — 스케줄 계산 엔진 ★ 핵심 ✅ 완료

`src/shared/scheduler/`. DB도 React도 모르는 순수 함수만.

```ts
resolveAnchor(date, anchorOverride: Anchor | null, weekdayAnchorTimes): string  // 'HH:MM', 항상 값이 나온다

layoutDay(input: {
  anchorTime: string,             // resolveAnchor 결과. null 없음
  localEvents: LocalEvent[],      // order_index 정렬됨
  googleEvents: GoogleEvent[],    // 절대 시각, 고정
  todoSlots: TodoSlot[],          // 절대 시각, 겹침 허용
  settings: { dayStartHour, moveUnitMinutes },
}): {
  blocks: PlacedBlock[],          // 계산된 start/end
  overflow: LocalEvent[],         // 하루 경계를 넘어 다음 날로 갈 항목
}
```

구현 순서 — 각각 테스트를 먼저 쓴다.

1. `getLogicalDate(now, dayStartHour)` — 새벽 3시 = 어제
2. `getWeekRange(today, weekStartMode)` — 요일 고정 3종 + 롤링 2종 (큰 위젯 전용)
3. `resolveAnchor` — `anchors` 행 있으면 그 값, 없으면 요일 기본값. 앵커가 없는 경우는 존재하지 않는다
3-1. `snapUpToUnit(time, 30)` — 06:40 → 07:00, 07:00 → 07:00 (정각은 그대로). 앵커 자동 설정과 `moveUnitMinutes` 스냅이 공용으로 쓴다
4. 앵커부터 누적 소요시간으로 시각 채우기
5. 구글 이벤트와 겹치면 → 해당 구글 이벤트 종료 시각까지 큐 전체 밀기
6. 하루 경계 초과분 → `overflow`로 분리
7. `resize` / `reorder` → 뒤 항목 표시 시각만 재계산 (당김·밀림 대칭)
8. 겹치는 블록의 나란히 배치(반쪽 폭) 계산 — 구글끼리, TODO끼리

**완료 기준**: 기획서의 시나리오("게임1 1시간 줄이고 게임4 삽입" 등)가 전부 테스트 케이스로 존재하고 통과. → **확인됨** (70개 테스트 통과)

구현하며 정한 것:

- **하루 좌표계**: 모든 배치 계산을 "논리적 하루 시작으로부터의 분(0~1440)"에서 한다. 자정 기준으로 계산하면 `dayStartHour=6`일 때 새벽 2시가 "어제 20시간째"라는 사실을 매번 따로 처리해야 하고 그 자리에서 부호 실수가 난다.
- **겹침 열 배정 순서**: 시작이 같으면 **긴 블록을 먼저** 놓는다. 짧은 것을 먼저 놓으면 감싸는 일정이 오른쪽 열로 밀려 곁가지처럼 보인다. 완전히 같은 구간은 id로 순서를 고정해 렌더 결과가 실행마다 흔들리지 않게 한다.
- **경계를 넘는 구글 이벤트**: `end <= start`면 하루 경계를 넘는 것으로 보고 이 날짜 몫만 잘라 하루 끝까지로 본다. 나머지를 다음 논리적 날짜의 항목으로 내보내는 것은 동기화 계층(Phase 7)의 책임.
- **overflow는 계산만 한다**: `layoutDay`는 넘치는 항목을 알려주기만 하고 DB를 고치지 않는다. 실제 이월(다음 날 재배정)은 Phase 6의 스케줄러가 한다 — 순수 함수를 유지하기 위함.

**완료 기준**: 마우스만으로 하루 계획을 처음부터 끝까지 짤 수 있다. → **확인됨** (CDP로 UI를 실제 조작해 13개 항목 검증)

구현하며 정한 것:

- **쓰기 채널은 하나**: 액션마다 IPC 채널을 만들지 않고 `Mutation` 판별 유니온 하나로 받는다. 액션이 십수 개가 되어도 계약·preload·핸들러 세 곳에 같은 이름을 반복해 적지 않는다.
- **드래그 정렬의 떨림 방지**: 삽입 위치를 화면의 현재 배치로 판단하면, 자리를 바꾸는 순간 뒤 항목이 밀리며 기준 중간점도 함께 움직여 두 자리를 왕복한다. 그래서 **끌고 있는 항목을 뺀 배치**를 드래그 시작 시 한 번 계산해 그 중간점들을 기준으로 쓴다.
- **`setPointerCapture`는 감싼다**: 예외가 나면 그 아래 리스너 등록까지 건너뛰어 드래그가 조용히 죽는다. 캡처에 실패해도 드래그 자체는 동작해야 한다.
- **확정 후에는 반드시 다시 읽는다**: 낙관적 갱신은 드래그 중 미리보기에만 쓴다. 밀림 결과는 파생 계산이라 화면에서 추측하면 실제 저장값과 어긋난다.
- **선택 액션바는 하단 고정**: 30분 블록은 높이가 20px 남짓이라 그 안에 버튼을 넣거나 팝오버를 띄우면 위젯 밖으로 나가거나 서로 겹친다.
- **샘플 데이터 버튼 제거**: 전체를 지우고 다시 넣는 동작이라 실제 입력 UI가 생긴 뒤로는 오조작 위험만 남는다. `npx electron . --seed`로만 실행한다.

**완료 기준**: 재부팅해도 같은 자리·같은 크기·같은 모드로 돌아온다. → **확인됨** (UI 조작 12개 + 클릭 통과 8개 검증)

구현하며 정한 것:

- **위치는 하나만, 크기는 모드별로 저장한다** (`widgetPosition: {x,y}` + `widgetSize: {small, large}`). 위치까지 모드별로 두면 펼칠 때 예전에 큰 위젯을 놔뒀던 자리로 창이 점프해 지금 보던 위치를 잃는다. **좌상단을 고정한 채 크기만 늘었다 줄었다** 하는 쪽이 예측 가능하다. 화면 밖으로 나갈 때만 안쪽으로 끌어당긴다.
- **저장된 좌표가 지금 붙어 있는 모니터 밖이면 무시한다.** 서브모니터를 떼고 켜면 창이 화면 밖에 생겨 영영 못 찾는다.
- **닫기 버튼은 숨기기다.** 진짜로 닫으면 트레이에서 다시 띄울 창이 없다. 실제 종료는 트레이 메뉴의 "종료"뿐.
- **크기 모드는 메인이 주인이다.** 창 기하와 묶여 있어 메인이 저장하므로, 바뀌면 `settings:changed`로 렌더러에 알려야 한다. (이걸 빠뜨려 창만 커지고 그리드는 2일에 머무는 버그가 있었다)
- **클릭 통과에는 탈출구가 필수다.** `setIgnoreMouseEvents`는 창 전체에 걸려 영역별 제외가 안 되므로, `forward: true`로 이동 이벤트만 받아 포인터가 설정 버튼·설정창 위에 있는 동안만 무시를 해제한다. 트레이의 "설정…"도 같은 목적의 두 번째 탈출구다.
- **잠긴 동안에는 호버 효과를 없앤다.** `pointer-events: none`으로 커서·호버·클릭을 한 번에 죽이고, 탈출 영역만 `auto`로 되살린다. 눌릴 것처럼 보이는데 안 눌리는 상태를 만들지 않기 위함.
- **트레이 아이콘은 코드로 생성했다** ([resources/gen-icon.mjs](../resources/gen-icon.mjs)). 이미지 라이브러리 없이 PNG를 직접 인코딩한다. 흰색 단색은 밝은 작업표시줄에서 사라져 중간 채도의 파랑을 쓴다.

구현하며 정한 것:

- **계산과 적용을 나눴다.** `planSlotRollover` / `planQueueRollover`는 순수 함수로 "무엇을 어디로"만 돌려주고, DB UPDATE는 메인의 잡이 트랜잭션 하나로 처리한다. 며칠 밀린 경우의 연쇄까지 테스트로 고정할 수 있다.
- **연쇄는 날짜 오름차순 한 번의 순회로 처리된다.** D-3의 초과분이 D-2로 가면서 D-2가 다시 넘치면 D-1로 — 앞 날짜부터 훑으면 자연히 이어진다.
- **오늘의 초과분은 옮기지 않는다.** 오늘은 아직 안 끝났고, 앵커를 미루거나 항목을 줄이면 다시 들어올 수 있다.
- **이월분이 하루 끝을 넘길 만큼 쌓이면 더 밀지 않는다.** 넘겨봐야 다음 논리적 날짜로 감겨 "오늘 이월분"이라는 의미가 깨진다. 남는 것은 하루 끝에 겹쳐 쌓인다.
- **날짜 감시는 1분 폴링이다.** 다음 경계까지 긴 `setTimeout`을 걸면 절전/최대 절전에서 깨어날 때 밀리거나 몰아서 뛴다. 정작 아침에 켰을 때 이월이 안 되어 있으면 안 된다. 비용은 1분에 문자열 비교 한 번.
- **히스토리의 날짜 묶기는 JS에서 한다.** `completed_at`은 ISO 타임스탬프라 `dayStartHour` 기준 날짜를 SQL로 계산하면 지저분하고, 새벽에 체크한 항목이 엉뚱한 날로 묶이기 쉽다.

- [x] 구글에서 삭제 (두 번 눌러야 나간다)

**완료 기준**: 구글 캘린더에서 수업 시간을 옮기면 위젯의 로컬 큐가 알아서 비켜난다. → **실제 계정 연결 후 확인 필요**

구현하며 정한 것:

- **`googleapis` 대신 `@googleapis/calendar` + `google-auth-library`.** 전체 패키지는 모든 구글 API를 담아 50MB가 넘는데 우리는 캘린더 하나만 쓴다 (0.8MB). 기획서의 `googleapis`에서 바뀐 부분.
- **자격증명은 `settings` 테이블에 두지 않는다.** `getAllSettings()`가 통째로 렌더러에 내려가므로 거기 넣는 순간 토큰이 화면 쪽으로 샌다. 별도 파일(`google-auth.json`)에 `safeStorage`로 암호화해 두고 메인에서만 읽는다. 렌더러에는 "있는지 여부"와 계정 이메일만 내려간다.
- **스코프는 최소로.** 전체 `calendar` 대신 `calendar.events`(이벤트 R/W) + `calendar.calendarlist.readonly`(목록 조회)만 받는다.
- **루프백 포트는 0으로 연다.** 고정 포트는 이미 쓰이고 있을 수 있다. 구글 데스크톱 앱 클라이언트는 `127.0.0.1`의 임의 포트를 허용한다.
- **종일 일정은 장애물이 아니다.** "종일 예비군"이 있다고 그날 저녁 큐가 통째로 밀리면 안 된다. 여러 날에 걸친 종일 일정은 날짜별로 쪼개 저장한다(id는 `원본id::날짜`) — 그러지 않으면 첫날에만 보인다.
- **삭제 반영은 `last_synced_at` 비교로.** 이번 동기화에서 안 보인 같은 기간의 행을 지운다. 기간 밖(예전에 받아둔 먼 미래)은 건드리지 않는다.

- **쓰기는 캐시를 손대지 않는다.** PATCH가 성공하면 동기화를 다시 돌려 구글이 실제로 저장한 값을 받아온다 — 시간대 보정이나 반복 인스턴스 처리 때문에 우리가 보낸 것과 다를 수 있고, 캐시를 손으로 고치면 5분 뒤 정기 동기화에 조용히 뒤집힌다. **실패 시 롤백 코드가 따로 없는 것도 이 구조 덕이다** — 캐시가 그대로이므로 다시 읽으면 원래 자리다.
- **자정을 넘는 일정에서 한 번 막혔다.** `end_time <= start_time`을 오류로 보면 23:00~00:00짜리 일정을 영영 못 고친다. 종료가 앞서 보이면 다음 날로 넘기는 게 맞다. 게다가 `dayStartHour` 때문에 논리적 날짜와 달력 날짜가 다르므로(새벽 2시 일정은 논리적으로 "어제"), 구글로 보낼 때는 달력 날짜로 되돌려야 한다.
- **홀드를 구글에도 요구한다.** 로컬은 실수로 순서가 바뀌는 정도지만 구글은 **남의 서버가 바뀐다.** 그래서 잠금을 풀어야만 끌 수 있고, 홀드 중에는 왼쪽 띠를 주황으로 바꿔 "지금 건드리면 반영된다"를 눈에 보이게 했다.
- **새 일정의 알림은 우리가 정한 것만 넣는다** (`reminders.useDefault: false`). 캘린더마다 기본 알림이 달라서 그대로 두면 위젯에서 만든 일정의 알림이 제각각이 된다. 기본은 **팝업 10분 전**이고 설정에서 없음~60분으로 바꾼다. **이메일 알림은 넣지 않는다** — 위젯에서 툭툭 만드는 일정이 전부 메일로 오면 메일함이 잠긴다. 실측 확인: `overrideReminders: [{method:'popup', minutes:10}]`.
- **만들 수 있게 했으면 지울 수도 있어야 한다.** 생성만 붙이면 잘못 만든 일정을 고치러 매번 브라우저를 열어야 한다. 그래서 삭제도 함께 넣되, **이 앱의 유일한 되돌릴 수 없는 조작**이라 우클릭 메뉴에서 **두 번 눌러야** 나간다. 자동 판단(밀림·이월·자연어 명령)은 이 길로 오지 않는다.
- **`is_held`는 구글이 모르는 로컬 컬럼이다.** 홀드 토글은 네트워크를 타지 않고 로컬 DB만 바꾼다 (`replaceGoogleEvents`가 이 값을 보존한다).

**주의**: `electron-store`는 v11이 ESM 전용이라 CJS 번들에서 `require`가 생성자를 못 받는다. v8(CJS)을 쓴다.

## Phase 8 — 자연어 명령 ✅ (1차)

원래 Post-MVP였으나 앞당겼다. Anthropic Messages API에 도구를 물려 "내일 저녁에 캡스톤 미팅 1시간"을 그대로 알아듣게 한다.

- [x] API 키 저장 (`llm-auth.json` + `safeStorage`, 메인 전용)
- [x] 도구 정의 + 실행 (`src/main/llm/tools.ts`)
- [x] 도구 루프 (`src/main/llm/agent.ts`)
- [x] 위젯 위에 뜨는 별도 입력 창 (`src/main/command-window.ts`) + 미배치 TODO 머리의 ✨ 진입점
- [x] 창 드래그 이동 + 위치 기억 (`settings.commandPosition`)
- [x] 설정 > 명령 입력 (키 입력, 모델 선택)
- [x] 명령으로 만든 항목의 카테고리를 모델이 고름
- [ ] 삭제 도구 + 실행 전 확인 UI
- [ ] 전역 단축키로 바로 열기

구현하며 정한 것:

- **대화가 아니라 명령이다** (기획서: input-only, 되묻기 없음). 답변 말풍선도 결과 로그도 없고, 피드백은 위젯이 실제로 바뀌는 것으로 준다. 시스템 프롬프트도 "애매하면 되묻기"가 아니라 "애매해도 가장 그럴듯한 해석으로 즉시 실행"으로 지시한다. 되물어봐야 사용자에게 보이지 않으므로 아무 일도 일어나지 않는다.
  - **예외는 아무 일도 하지 못했을 때뿐.** 그때만 이유를 한 줄 띄운다 — 안 그러면 먹통으로 오해한다.
- **대화 기록을 남기지 않는다.** 매 호출이 독립이고 맥락은 그때그때 만든 스냅샷이 전부다. 처음에는 대화 id로 기록을 들고 있었지만, 화면에 보이지 않는 맥락 때문에 같은 명령의 결과가 달라지는 건 예측 불가능하다.
- **위젯 안 드롭다운이 아니라 별도 창.** 백로그는 위젯 맨 아래에 붙은 스크롤 영역이라 안에서 펼치면 창 밖으로 잘리거나 목록을 가린다 (실제로 처음 만든 드롭다운이 아래로 잘렸다). 렌더러 번들은 하나를 공유하고 `main.tsx`가 `?view=command`로 어느 쪽을 그릴지 고른다.
- **SDK 대신 `fetch` 직접 호출.** 엔드포인트가 `/v1/messages` 하나뿐이다. 메인은 CJS로 번들되므로 ESM 전용 패키지를 물었다가 `require`에서 깨질 여지를 만들지 않는다 (`electron-store` v11에서 겪은 함정).
- **API 키는 `settings` 테이블에 두지 않는다.** 구글 자격증명과 같은 이유 — `getAllSettings()`가 통째로 렌더러에 내려간다. 렌더러에는 "있는지"와 꼬리 4자만 간다.
- **삭제 도구를 주지 않았다.** 되돌릴 수 없는 조작을 모델 판단에 맡기면 오해 한 번에 기록이 사라진다 (설계 원칙 6). 되돌릴 수 있는 것만 준다 — 완료 체크, 배치 해제(백로그로), 시간 이동. 진짜 삭제는 사용자가 그리드에서 우클릭으로 한다.
- **구글 캘린더는 읽기만 한다.** 쓰기(`events.insert`/`patch`)를 한 번 붙였다가 걷어냈다 — 원칙 3대로 구글 이벤트는 고정 장애물이지 우리가 쓰는 대상이 아니다.
- **시스템 프롬프트에 현재 일정 스냅샷을 매번 새로 넣는다.** 굳혀두면 모델이 옛 상태를 보고 판단한다. 스냅샷은 화면과 **같은 `layoutDay`**를 거쳐 계산된 시각까지 담는다 — 저장값(순서 + 소요시간)만 주면 "저녁 8시"를 알 수 없다. 계산 결과는 어디에도 저장하지 않는다 (설계 원칙 1).
- **도구가 던진 오류는 루프를 끊지 않는다.** `is_error` 결과로 모델에게 돌려주면 날짜 형식 정도는 스스로 고쳐 다시 부른다.
- **쓰기 입구를 하나로 모았다.** `applyMutation`(`src/main/db/mutations.ts`) — IPC 핸들러와 명령 도구가 같은 함수를 쓴다. 두 벌이면 한쪽만 고치는 사고가 난다. 읽기도 마찬가지로 `loadScheduleData`(`src/main/db/schedule-view.ts`)로 모았다.
- **갱신 알림은 위젯 창으로 보낸다.** 명령은 별도 창에서 오므로 `e.sender`로 보내면 명령 창 자신이 받고 정작 위젯은 낡은 채로 남는다.
- **기본 모델은 Haiku 4.5.** 하는 일이 "한 줄 → 도구 호출"이라 추론이 거의 없고, 위젯에서 치고 바로 닫는 흐름이라 지연이 곧 손해다. 실측으로 세 갈래(시각 지정 / 그날 할 일 / 백로그)를 다 맞게 골랐다.
- **무엇으로 만들지 고르는 규칙을 프롬프트 맨 앞에 표로 뒀다.** 처음에는 "TODO 슬롯은 시각이 정해진 일"이라고 설명 안에 묻어뒀더니 Haiku가 "8시에 과제 40분"을 `create_event`(앵커 큐)로 만들었다 — 그러면 시각이 통째로 무시된다. 틀리기 쉬운 판단은 설명이 아니라 규칙표로 먼저 준다.
- **"오늘/내일"을 모델에게 계산시키지 않는다.** 스냅샷의 날짜마다 `relative`(어제·오늘·내일…)를 붙여 보낸다. 벽시계로 더하게 두면 새벽에 하루씩 밀린다 — 8월 6일 02시는 논리적으로 아직 8월 5일이라, 그때의 "내일"은 8월 7일이 아니라 8월 6일이다. 라벨 계산은 `relativeDayLabel`로 순수 계층에 두고 테스트로 고정했다.
- **카테고리는 명령으로 만들 때 그 자리에서 정한다.** 기획서는 별도 큐(`ai_classification_queue`) + 배칭 + 백오프를 설계했지만, 이미 모델을 부르는 김에 고르게 하면 큐가 통째로 필요 없다. 손으로 만든 TODO의 백그라운드 분류는 여전히 스코프 밖.

## 시간 입력 단위 ✅

1분 단위 입력이 스크롤로 맞추기 번거로워 전부 굵게 바꿨다. **화면에 1분 단위 입력은 더 이상 없다.**

| 무엇 | 단위 | 상수 |
|---|---|---|
| 앵커 (날짜 머리 · 요일 기본값) | **30분** (00/30) | `ANCHOR_STEP_MINUTES` |
| TODO 슬롯 · 구글 일정 시각 | **10분** | `TIME_STEP_MINUTES` |
| TODO 마감 (`datetime-local`) | **10분** | `TIME_STEP_MINUTES` |
| 드래그 이동/리사이즈 | **10~50분** 중 선택 (기본 30) | `MOVE_UNIT_CHOICES` |

- **`<input type="time">`으로는 애초에 불가능했다.** `step={600}`을 줘도 **Chromium 네이티브 피커가 이를 무시하고 분을 00·01·02…로 나열한다** (화면 캡처로 확인). 그래서 시각 입력을 전부 `TimeField`(시/분 `<select>` 두 개)로 직접 그렸다 — 고를 수 있는 값 자체가 격자다. 격자 밖 값(구글에서 온 14:07 등)은 목록에 끼워 넣어 그대로 보여주고, 한 번 고르면 격자 값으로 바뀐다.
- 앵커를 30분으로 올린 이유: 그날 큐 전체의 출발점이라 정밀할 이유가 없고, 부팅 자동 앵커(`ANCHOR_SNAP_MINUTES`)와도 격자가 같아진다. 기획서의 "15분 단위(00/15/30/45)" 확정은 이걸로 대체한다.
- 이동 단위에서 15·60분이 빠졌다. DB에 남은 예전 값은 설정 검증에서 걸러져 기본값(30)으로 되돌아간다 (테스트로 고정).

- [x] `better-sqlite3`가 설치본에서 동작 (`asarUnpack: ["**/*.node"]` → `app.asar.unpacked`)
- [x] 데이터 폴더를 이름에서 떼어냄 — 개발/설치본이 같은 DB·토큰·API 키를 쓴다
- [x] 개발 빌드가 남긴 시작 항목을 설치본이 이어받음

구현하며 정한 것:

- **`userData`를 못 박았다** (`app.setPath('userData', …)`). 기본값은 `app.getName()`에서 나오는데 그 이름이 개발(package.json `name`)과 설치본(`productName`)에서 달라진다. 그대로 뒀으면 설치하는 순간 **일정·구글 토큰·API 키가 전부 사라진 것처럼 보였을 것**이다. `whenReady` 전에 정해야 한다.
- **실행 파일 이름은 ASCII로**(`win.executableName`). 제품 이름은 한글로 두되 exe는 `weektodo-widget.exe`라 경로를 다루는 도구들이 덜 까다롭다.
- **시작 항목 이관에서 두 번 막혔다.**
  1. `launchItems[].args`는 `--`로 시작하는 플래그를 **빼고** 돌려준다. `args.includes('--autostart')`로 우리 항목을 찾으려던 시도가 항상 빈손이었다.
  2. `launchItems`는 **지금 실행 중인 실행 파일과 경로가 같은 항목만** 돌려준다. 그래서 설치본에서는 개발 항목이 아예 보이지 않아 지울 수가 없다.
  → 결국 **우리가 만든 항목의 레지스트리 값 이름을 설정에 기억**(`launchAtLoginItems`)하고, 다른 빌드가 그걸 보고 지우는 방식으로 갔다. 자동 실행 여부도 레지스트리가 아니라 `launchAtLoginEnabled`에 저장한다 — 실행 파일이 바뀌면 레지스트리는 "꺼짐"으로 보이는데 그걸 사용자가 끈 것으로 오해하면 안 된다.
- 값 이름은 앱 이름에서 나온다: 개발 `electron.app.Electron` → 설치본 `electron.app.주간 타임블록`.

## 확정된 결정

기획서에서 모호했던 부분은 아래로 확정되었다. 스키마 반영 위치는 각 Phase 참고.

### A. 앵커는 항상 존재한다 ✅
"앵커 없는 날"이라는 상태 자체를 없앤다. 요일별 기본 앵커 시각(`settings.weekdayAnchorTimes`)이 항상 값을 주고, `anchors` 테이블은 그에 대한 **override 기록**일 뿐이다. `local_events`는 `anchor_id` 대신 `date`에 매단다.
→ 계산 엔진에 `anchor: null` 분기가 사라져 Phase 2가 단순해진다. 큐만 있고 시각이 비어 있는 중간 상태도 없어진다.

### A-1. 앵커 자동 설정 = 시작앱 실행 시각 ✅
PC 부팅 후 이 앱이 **시작앱으로 자동 실행된 시각**을 30분 단위로 올려(06:40 → 07:00) 그날 앵커로 자동 기록한다. 요일 고정값보다 "실제로 책상 앞에 앉은 시각"에 가까우므로 이쪽이 더 나은 추정치다.

우선순위: **사용자 수동 지정 > 부팅 자동 기록 > 요일 기본값**. 앞의 둘은 `anchors` 행으로, 마지막은 파생으로 표현되므로 해석 로직은 여전히 2단계다(행이 있나? 없으면 요일 기본값).

부팅 시각을 DB에 저장하는 것은 원칙 1(파생값 저장 금지)에 어긋나지 않는다 — 관측된 사실이기 때문이다. 오히려 저장하지 않으면 어제·그제 컬럼이 나중에 요일 기본값으로 재계산되어 **과거 큐 시각이 실제와 달라진다**.

구현 함정 두 가지 (Phase 5 참고): Windows에는 `wasOpenedAtLogin`이 없어 `--autostart` 인자로 판별해야 하고, 새벽 재부팅은 `getLogicalDate` 기준 아직 어제이므로 어제 앵커를 덮어쓰면 안 된다.

### B. 이월 위치 = 다음 날 앵커 ✅
"맨 앞"은 **다음 날 앵커 시각에 붙이는 것**으로 확정. duration은 유지하고, 여러 개면 앵커부터 순차로 이어 붙인다(전부 겹쳐두면 폭이 1/N로 쪼개져 못 읽음). `todo_time_slots`는 절대 시각 유지 — 스키마 변경 없음.

### C. 구글 캐시의 로컬 상태 ✅
테이블 분리 없이 `INSERT ... ON CONFLICT DO UPDATE`로 구글 필드만 갱신하고 `is_held`·`created_at_original`은 보존한다.

### D. 로컬 이벤트 완료 — 카테고리별 ✅
카테고리에 `completable` 플래그를 두고, 시드에서는 **과제만 1**. `local_events`에 `completed`/`completed_at`을 두되 체크박스 노출은 이 플래그로 판단한다. "밥", "게임1"에는 체크박스가 안 뜬다.
→ 나중에 다른 카테고리도 체크하고 싶어지면 설정에서 켜면 되고, 코드 변경이 필요 없다.

### E. 위젯 크기 모드 ✅
작은 위젯은 **오늘 + 내일 고정**. `weekStartMode`(토/일/월/어제/오늘)는 **큰 위젯 7일의 시작 기준**을 정하는 설정으로, 작은 위젯에는 적용하지 않는다.
